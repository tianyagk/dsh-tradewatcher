### 1.7 六个重点问题的展开结论

**Q1 报告状态机 + 不可变版本哈希：值不值得做？落在哪？最小形态？**

**不做状态机。** 状态机的每一个状态都由"有人在应用内生成内容、且生成会失败、失败值得自动重试一次"驱动（Hanai 的 `repairing` 会重新驱动**同一个 DSH session**）。我们的报告生成方**就是**会话里的 agent：重试 = 用户再说一句，进度 = 会话本身。在插件里再造 `generating/verifying/repairing` 等于给同一次生成维护第二套状态，而我们的"校验器"只有源码级扫描（`markdownScan.test.ts`），对一个运行时生成的正文没有任何判据可用。

**若确实需要"一份东西"**，最小形态（**成本 S**，不新增页签）：

- 落点：工具箱第 3 张卡（`src/client/toolRegistry.ts:225` 加一行 + `src/client/tools/brief.ts` 一个文件），或复盘页的「复制本日摘要」按钮。
- 实现：**纯函数**把**既有载荷**渲染成 Markdown（蛋糕 `api.globalFlow` + 护盘 `api.rescue` + 持仓 `api.portfolio` + 日历 `api.calendar`），固定头部四行：`生成时刻` / `数据时刻` / `缺失 N 项（逐条原因）` / `口径版本`。
- 不做：状态机、修复预算、内容寻址目录。要"不可变"就复用 `src/host/backup.ts:52` 的 `filesChecksum` 形状（`schemaVersion` + 内容哈希 + 导入时比对）。
- **拒绝**：sha256 目录树、`0001.staging` 命名、逐字段幂等恢复 —— 它们解决的是"多进程/多次重试写同一目录"的问题，我们没有这个写入模式。

**Q2 来源五元组 + `cacheState` 四态：要不要统一成一个契约？代价多大？**

**只统一"新载荷"，不重写旧的。** 现状是：agent 侧**已经**统一（`DataProvenance` + `tools.ts:65-93` 打印），界面侧有 5 种形状（`src/client/api.ts` 里 `missing` 四种写法 + 部分载荷只有 `asOf` 无 `missing`）。

| 方案 | 改什么 | 代价 | 收益 |
|---|---|---|---|
| A 全仓统一（把 5 种形状收敛成 `DataProvenance`） | `api.ts` 30 条路由回包 + 6 个页面 + 客户端视图模型 + 约 40 断言 | **L**（且几乎每天都有新回包，迁移期双写） | 形状整齐；用户**多知道的事**是 0（他看的是界面，界面早就按需显示了） |
| B 只对新载荷做 lint（推荐） | 一条源码级断言：`api.ts` 新增的 `*Dto` 必须含 `asOf` + `missing`，例外进白名单并写理由 | **S** | 防"下一个载荷忘带出处"（这正是 `AUDIT-HY4-1` 那类事故的入口） |

**不新增字段的理由**：`fetchedAt`（取数时刻）在我们的语义里被 `asOf`（观测时刻）+ `breakerSummary`（失败时刻）分开承担（`README.md:299`："失败时刻与数据时刻分列"），加第三个时间字段会让"这个数是几点"变成三选一。`cacheState` 单枚举不采纳：`cached`（休市定稿零回源）与 `stale`（降级复用）**可以同时为真**，单枚举表达不了（`model.ts:1353`）。

**Q3 曲线叠加：杠杆工具/蛋糕工具是否需要多曲线叠加？成本（手写 SVG 80 行 vs 我们现有实现）？**

**已有，且比参照实现更适合我们；首值归一不采纳。**

| 能力 | skills-stock（约 80 行手写 SVG） | 我们（`ToolsPage.tsx:892-1096`） |
|---|---|---|
| 多序列同图 | 有 | 有（`series: ToolCurveSeries[]`） |
| 共同 y 域 | 有（`bounds`） | 有（`:906-947`，跨序列取 min/max） |
| 缺值处理 | 无（数组等长） | **断线不连**（`:955-957`，`null` 就 `open=false`）——不画假线 |
| x 轴 | **按各自长度归一**（第几个点）⇒ 跨 run 日期错位会失真 | **时间轴**（`days[]` + `plotX`，两端标真实日期 `:1060-1061`） |
| 双量纲 | 只能各自归一 | **双轴 + 独立刻度 + 柱区小轴**（`leveragePage.tsx:16-18`） |
| 长度不一致直说 | 图例写 `len/maxLen` | 覆盖报告写「本地拼接 3/5 天 · 缺 2026-10-07」（`README.md:30`） |

唯一还值得留意的是归一的**触发条件**：真要做「组合净值 vs 沪深300」时两者量纲不同，那时才需要首值归一 —— 但前置是**每日组合净值快照**，我们**没有**（仓内无 equity/净值序列，`portfolio.ts` 只算当下横截面）。所以：**暂缓，且触发条件是"先有净值序列"**，不是"先有图表函数"。

**Q4 因子评价（IC/RankIC/分桶/IC 半衰期）：本插件是行情监控不是量化研究，值得纳入吗？**

**不纳入。** 三条理由，按强度排序：

1. **无输入**：IC 需要"因子值 × 未来收益"的横截面矩阵；我们没有因子面板、没有收益率矩阵、没有 point-in-time 数据。没有输入的功能只能做成演示。
2. **定位不符**：本插件的产出是"现在发生了什么"（行情/持仓/护盘行为/筹码分布），不是"哪个因子还能用"。ROADMAP 的排序原则已经写明："先让已有数据不说谎 → 再外化状态 → 最后做加法"（`docs/ROADMAP.md:9`）。
3. **已有更保守的替代**：`src/host/signalForward.ts` 给"过去 N 次信号之后发生了什么"，**强制带基准与持有期**、样本 <10 明确标注"不构成统计结论"、并且明写"不能说有预测能力"（`:1-18`）。IC 的天然话术是"这个因子有效"，恰好是 `signalForward.ts` 花整段注释去避免的那句话。

**若将来仍要做**，前置是 recon §3 已经暴露的那个坑：`layered.js:75` 用同一根 bar 的收益对因子求均值 ⇒ **自己都有前视**。在没有 `data_pit` 概念之前引入 IC，等于把一个有前视的指标摆到面板上。

**Q5 双盲隔离 + 审计员清单 + PII 退出码：哪一部分能改造成"数据质量闸门"？最小方案？**

能改造的是**审计员 A–G 的"可检查性"**，不是双盲（单用户没有角色），也不是 PII 退出码（我们不落盘任意产物）。最小方案（**成本 S–M**）：

**一层：`src/shared/payloadGate.ts`（纯函数，不 import React、不碰 IO）**

对**渲染模型**（不是原始载荷）跑三类检查 —— 因为事故都发生在"载荷有、渲染丢"这一步：

| 检查类 | 判据（每条都要能给出路径与原因） | 对应 A–G | 我们已发生过的实证 |
|---|---|---|---|
| `source` | 每个数值格，要么有来源声明（`source`/`note`/`caliber`），要么在 `missing[]` 里；**不允许"有值但无出处"** | A + G | `globalFlowView.ts:221` 全缺时给 `0.00%` |
| `date` | 载荷级 `asOf` 存在（可为 `null`）；`asOf === null` ⇒ `missing[]` 必须非空；超出频率阈值 ⇒ `lagAlert` 必须出现 | B | `lagAlertOf` 已实现，但未对所有载荷统一强制 |
| `caliber` | 声明里的常量与数据自洽：窗口长度 == 序列长度、有效点 + `null` 点 == 总点数、份额合计 == 100、六因子贡献度之和 == 总分 ±0.5、三类家数之和 == 总数 | C + D | `AUDIT-HY4-1.md:323` 自校算了但丢了；`src/host/p0.test.ts:83-94` 已有贡献度 == 总分 ±0.5 的单点断言（闸门只是把它复用到**所有**载荷） |

**二层：`src/shared/payloadGate.test.ts` 双向注入（抄 `test_gate.py` 的"必拦/必放"）**

- **必拦**：① 把某格的值改成 `0` 并删掉对应的 `missing` ⇒ `source` 类必报；② 把 `asOf` 置 `null` 且 `missing: []` ⇒ `date` 类必报；③ 把份额改到合计 97% ⇒ `caliber` 类必报。
- **必放**：当天的真实载荷 fixture（`globalFlow` / `leverage` / `rescue` 各一份**脱敏落盘样本**）必须 **0 问题**。
- **白名单**：允许逐条豁免（例如"该格是纯标签不含数值"），每条豁免必须写一句理由 —— 且断言"白名单条数不得增长"（新增豁免要改测试，改测试就要评审）。这条照抄 `src/host/usQuote.test.ts:248` 的接入面断言写法（它用 `deepEqual(importers, [...])` 锁死 `robotsGate` 的接入面）。

**为什么这是最小方案**：不改任何用户可见文案、不改任何口径、不新增路由、不新增依赖；它只是把"我们已经在各处零散断言的 A/B/C/D/G"收成一件可复用的东西，并首次给出**双向**判据。

**双向测试我们已经有先例**：`src/assertStrength.test.ts:1-18` 就是"同一份判据对**坏样本必须命中 / 好样本不误报**做双向对照"，且它自己在注释里写明"自证非恒真"。R1 只是把这个已经证明有效的测试形式，用到"数值诚实性"这一类判据上 —— 不是引入新方法论。

**Q6 能力目录 + DatasetRef：工具页只有 2 个工具，是否需要？将来 >5 值不值得提前建？**

**现在不需要，将来也不建议"提前建"。** 三条依据：

1. **规模**：Capital 的问题是有 128 个能力（61 个挂在同一把密钥上）。我们是 12 个 agent 工具 + 2 个 UI 工具；工具描述合计 4018 B，`systemPrompt` 那一段是整段常量（`src/host/tools.ts` 的 guidance）。远没到"必须二级间接"的量级。
2. **UI 侧已经是目录形态**：`ToolEntry`（`toolRegistry.ts:39-83`）就是"卡片一行 + 详情按需"：`catalogModel` 只取 id/chip/name/blurb，`detailModel` 才展开结构（`:261-270`、`:328-407`）。再包一层 `DatasetRef` 只会多一次往返。
3. **DatasetRef 的前提是"数据集大且可复用"**：我们的回包是几百字节到几 MB（筹码回包有 256 KB 预算，`chips.ts:53-60`），而且**没有跨工具复用同一份数据集**的场景（蛋糕只被工具箱用，杠杆只被杠杆页用 —— 这正是行归属判据 `DESIGN-SUBPLUGINS.md:75-77` 的结论）。
