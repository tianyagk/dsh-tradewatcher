## 二、结论：**推断不成立**（单位没有混）

`top` 的**值**是 `0.1`（分数），只有**标签**是 `"10.000%"`（`value × 100` 后加 `%`）；`widthOf(w) = w / top × 100`
入参出参都是同一套约定 ⇒ `0.0863 / 0.1 × 100 = 86.3%` ✅。**当前工作区里不存在"0.86%"这条路径**。

**那截图里的 ~0.2% 从哪来？** 我手上没有浏览器，只能给两个可验证的假设（都在报告里标明是假设）：
1. **前端 bundle 是旧的**（最可能）：客户端改动只有**刷新页面**才会生效（除非 `pnpm run dev:web` 在跑）。
   这条"第二次报"很可能仍是 **task-69 之前**的 JS —— 那时的条宽是 `(w / max) * 100%`，而 `max` 与轴顶不同尺度，
   正好会画出"极短条 + 轴到 10%"的观感。**请先硬刷新（Ctrl/Cmd+Shift+R）再看一次**；
2. 若刷新后仍是短条，则问题在**布局宽度**（`.tw-chips-plot` 被左轴/语义线标签挤窄）而非数值 —— 那时请给我
   DevTools 里 `.tw-chips-bars` 的 `clientWidth` 与某根 `.tw-chips-bar` 的 `width` 计算值，我按这两个数定位。

## 三、本批实际改动（按 task-79 的 ②/④ 做加固，未改行为）

1. **单位约定写死在签名与注释里**（`src/client/chipsView.ts` 的 `ChipAxis` 前）：
   `peak`/`top`/`step`/`widthOf` 的**入参**一律**分数**（0–1，与 `buckets` 同单位）；`ticks[].pct` 与 `widthOf` 的**返回值**一律**百分数**（0–100）；
   **跨单位只允许在边界处显式 × 100 一次**。
2. **几何锚定断言**（`chipAxis.test.ts` 新增，不再"函数 vs 它自己"）：
   - 真实量级 fixture（`peak = 0.0863`、`top = 0.1`）⇒ `widthOf(peak) ∈ [80%, 90%]`（混单位时这里会是 **0.86%** ⇒ 必被抓）；
   - **轴顶对应的桶宽度必须 === 100%**；
   - `peak === top`（单桶 10% 顶到轴顶）⇒ 条宽 === 100%；
   - **单位契约**：`widthOf(...)` 返回值 `> 1 且 ≤ 100`（是百分数，不是分数）；
   - **渲染层静态核对**：必须是 `width: ${axis.widthOf(w)}%`，且**不许**再乘一次 100（防"函数对、渲染又乘"）。
3. **`bucketCenterTicks` / `axisTicks` 单位核查**（task-79 ④）：两者入参出参都是**价格**（元），不涉及"分数 vs 百分数"，
   与 `centers` 同单位 ⇒ **没有混单位，未改动**（未扩大范围）。
