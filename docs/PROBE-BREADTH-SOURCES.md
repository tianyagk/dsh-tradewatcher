# 全市场涨跌分布：不依赖东财的数据路径实测

> 任务：为「全市场涨跌分布 / 涨跌家数」找一条不依赖东财的可用路径，逐个实测并给出成本模型。
> 约束：只读，不装包，不改 `src/**`。侦察员：recon-week｜实测时间：**2026-10-26 20:33–21:05**（周一收盘后，全部为当日收盘数据）
> 仓库基线：`c0682f6`（v0.175.0）
> 标记：**实测** = 本次真实发过请求并读到响应；**未确认** = 没打通或没验证

---

## §0 背景：东财通道确已不可用（复测）

| 端点 | 结果 |
|---|---|
| `https://push2.eastmoney.com/api/qt/clist/get?...` | **HTTP 000**，`curl(52) Empty reply from server`，0.05 s |
| `https://push2his.eastmoney.com/api/qt/stock/kline/get?...` | **HTTP 000**，`curl(52) Empty reply from server`，0.08 s |

不是 DNS 失败、不是超时、不是 403 ——是**服务端直接断连**（空回复）。与 Lead 描述一致，故东财系整体排除。
→ 注意：后文腾讯在超大批量下失败时也是同样的 `HTTP 000 / curl(56)`，**所以"000"不能单独用来判断"网络不通"，必须看 curl 错误码**。

## §2 端到端验证：两条路线算出同一个分布

同一时点（2026-10-26 收盘后）分别跑两条独立路线，11 档口径完全对齐：

| 档位 | 腾讯路线（5,577 只） | 新浪路线（5,574 只） |
|---|---:|---:|
| > +10% | 52 | 56 |
| +7 ~ +10% | 64 | 60 |
| +5 ~ +7% | 71 | 72 |
| +3 ~ +5% | 231 | 231 |
| 0 ~ +3% | 1,834 | 1,833 |
| **平盘 0%** | **168** | **165** |
| 0 ~ −3% | 2,156 | 2,158 |
| −3 ~ −5% | 590 | 589 |
| −5 ~ −7% | 229 | 228 |
| −7 ~ −10% | 140 | 143 |
| < −10% | 42 | 39 |
| **上涨 / 下跌 / 平盘** | **2,252 / 3,157 / 168** | **2,252 / 3,157 / 165** |

**上涨家数与下跌家数两源完全一致（2,252 / 3,157）**；差异只有 **3 只停牌股**（腾讯把它们按 `0.00%` 计入平盘，新浪返回 `0.000` 价被过滤）。→ 两源互证成立，**口径差异必须显式定义**（见 §4.3）。

> 相邻档位 ±1~2 只的抖动，来自"腾讯用服务端预算的涨跌幅、新浪用现价/昨收自算"的浮点舍入边界，属正常。

## §3 结论

### 3.1 最可行 1 条：**腾讯批量报价 + 交易所代码表**

| 项 | 结论 |
|---|---|
| **路径** | 代码表（每日一次，交易所官方）→ 腾讯 `qt.gtimg.cn` 按 **600/批** 取现价与涨跌幅 → 本地聚合 11 档 |
| **覆盖率** | **沪深京全市场 5,577/5,577 = 100%**（沪 2,318 / 深 2,906 / 京 353）；交易所三所列表与新浪 5,576 计数互相印证 |
| **鉴权** | **零鉴权**：腾讯无需 Referer、无需 Cookie；交易所列表只要 `Referer` 头 |
| **稳态成本** | **10 请求/轮**（5,577 ÷ 600 向上取整），顺序 **≈4.0 s**，4 并发 **≈0.9 s** |
| **限流风险** | **低**。本次连跑 **4 轮全量**（12+10+12+12 批）+ 单批压测，合计 **70+ 次请求，零失败、零 429**。真正的硬边界是**单批 600 只**（700 起 TCP 断连），不是频率 |
| **缓存** | 分布 **5–10 min**；代码表 **每日一次**（收盘后或次日盘前刷新） |

### 3.2 两版成本（按 Lead 追加约束：可接受 5–10 min 刷新、单轮 ≤180 s）

**A. 最省请求数方案 —— 新浪报价（800/批）**

| 项 | 数值 |
|---|---|
| 批数 | **7 批**（5,577 ÷ 800 向上取整；**1,200 起 431，800 是硬上限**） |
| 耗时 | 顺序 **3.9 s**；4 并发 **0.95 s** |
| 每轮请求 | **7**（代码表另计，每日 7 次） |
| 限流风险 | 低—中：**必须带 Referer**（无则 403）；本次 7 批 × 2 轮 + 56 页全量扫，**零 429** |
| 覆盖 | 99.9%（5,574/5,577，**3 只停牌返回空串被剔除**） |
| 代价 | 需自算涨跌幅（现价比昨收）；每批 178 KB，7 批 ≈ **1.2 MB/轮** |

**B. 最快方案 —— 腾讯报价（600/批，4 并发）**

| 项 | 数值 |
|---|---|
| 批数 | **10 批**（顺序）→ 4 并发 **3 波** |
| 耗时 | 顺序 **4.05 s**；**4 并发 0.90 s**；8 并发 0.74 s（不建议，收益递减且风险上升） |
| 每轮请求 | **10**（稳态，代码表已缓存） |
| 限流风险 | 低：无鉴权、无 429；**但单批 >600 会直接断连**，必须严守 600 |
| 覆盖 | **100%**（5,577/5,577） |
| 代价 | 腾讯**直接给涨跌幅**，不用自算；每批 ~300 KB，10 批 ≈ **3 MB/轮** |

**C. 兜底方案 —— 新浪全量列表（56 页，单源闭环）**

| 项 | 数值 |
|---|---|
| 批数 | **56 页**（100/页，`num` 被压回 100） |
| 耗时 | **11.96 s**（均值 212 ms/页，最慢 1.22 s） |
| 每轮请求 | **56**，**且不需要代码表**（列表自带代码+现价+涨跌幅+昨收） |
| 限流风险 | 低（本次 56 页连续跑完零失败） |
| 价值 | **单源即可完成**，适合"代码表损坏/首次冷启动/核对"；0 重复、覆盖 5,576 |

> **推荐组合**：主用 **B（腾讯 600/批，10 请求，4 并发 0.9 s）**；每轮结束用 `getHQNodeStockCount` 比对只数（1 请求）做健全性检查；每日用 **A 交易所列表**（7 请求）刷新代码表；每周用 **C** 跑一次全量对账。

### 3.3 为什么不是"1 请求"

市面上常见的"单请求返回涨跌家数"依赖专门聚合接口（乐咕乐股等），**本轮实测该接口 404、同花顺 403、雪球 400 需 Cookie、和讯 502**。东财 `push2` 原本承担这个角色，现已断连。→ **现状下"最省"就是 7 请求（新浪 800/批），不存在 1 请求的可靠方案。**

## §4 工程实现要点（按 Lead 约束）

### 4.1 批/页间延迟（防限流）

- 本次所有顺序测试都用了 **120 ms** 批间延迟，70+ 次请求零失败。
- 建议值：**顺序 120–200 ms；4 并发放宽到 200 ms/波**。
- 若出现 `429` 或 `curl(56)`：**指数退避**（1 s → 2 s → 4 s，最多 3 次），并**降并发到 1**。

### 4.2 失败可续扫

按 `(证券池版本, 批次索引)` 落检查点：

```
scan = { poolVersion: '2026-10-26', total: 5577, batchSize: 600,
         done: [0,1,2,...],  partial: { batch: 7, got: [....] }, startedAt }
```

- 单批失败**不丢弃整轮**：记录 `failedBatches: [7]`，继续跑其余批；结束后只重试失败批（≤3 次）。
- **代码表带版本号**：若中途代码表被刷新（新股上市），旧检查点的 `poolVersion` 不匹配就**整轮作废重跑**，避免"半新半旧池"。

### 4.3 停牌口径（必须显式定义）

实测两家对停牌处理不同：腾讯按 `0.00%` 计入**平盘**（168 只），新浪返回 `0.000` 价被**剔除**（165 只）。二者都"对"，但**不能混用**。建议：

- 先按 `现价 > 0 且 昨收 > 0` 过滤 → 得到"可交易样本"；
- **平盘 = 可交易样本中涨幅恰为 0**；
- 停牌单独一档 `suspended`，**不计入平盘也不计入涨跌**，并在 UI 标注"N 只停牌未计入"。

这与本仓库既有原则一致：**缺失要分类，不能拿 0 冒充**。

### 4.4 缓存

| 对象 | TTL | 失效条件 |
|---|---|---|
| **代码表** | **每日一次**（收盘后 15:30 或次日 08:30） | 三所列表任一拉取失败 → 保留旧表并标 `stale`；`getHQNodeStockCount` 与实际只数偏差 >0.5% → 强制重建 |
| **分布结果** | **5–10 min**（建议 5 min，交易时段） | 手动刷新立即失效；非交易时段可延长到 30 min |
| **单批报价** | 不缓存 | 每轮必须新取，否则分布滞后 |

## §5 未确认项

1. **北交所的 353 只是否等于全部京市 A 股**：`bse.cn` 返回 `totalElements: 353`，且新浪 `hs_a` 里 `bj` 前缀也正好 353 —— 两源一致，但**未与北交所官方"上市公司数"公告核对**。
2. **`node=hs_a` 的确切口径**：实测含 `bj`，但其文档未定义是否含 ST/退市整理/北交所全部层级；只验证了总数 5,576 与三所合计吻合。
3. **乐咕乐股新接口**：API 404，仅确认首页可达，**没有找到替代路径**（可能需要登录或已下线）。
4. **中证/国证是否有"市场统计"类接口**：只试探了 2–3 个路径，均 404 或空数组；**不等于它们没有**，只是本轮没找到。
5. **收盘后数据**：本次全部在 20:33–21:05 采样，取到的是**当日收盘定格值**。**盘中（09:30–15:00）的刷新延迟、限流阈值未测**——腾讯/新浪盘中是否降频，需交易时段复测。
6. **停牌 3 只的具体名单**未逐只核对（腾讯计为平盘、新浪剔除），只验证了数量差为 3。
7. **腾讯 600 批上限的成因**未确认：700 起为 `curl(56)` 断连，疑似 URL 长度（≈6.3 KB）或服务端 query 上限，**未做包大小/头部大小分离实验**。
8. **AkShare 结论为推断**：其代码未在本轮阅读，判断依据是"其 A 股宽度接口长期依赖东财 push2"，**未逐接口验证**。
