## 0. 一行结论

**根因是上游单位不一致，不是缓存损坏**：腾讯 `fqkline` 对**科创板（688）**回的成交量是**股**，东财回落是**手**，而本插件全链路按**手**算换手率 —— `mergeBars` 按日期拼接两段就留下 **≈100× 的段内断层**（用户池里 3 只科创板标的**全部**命中）；已按「只改量纲」修好：源侧 ÷100 + 读缓存时把旧段对齐到新段 + 读侧用同日报价兜底，**价格/日期一根不动**，落盘走 `updateJsonLocked`，并在回包/界面如实标注。

## 1. 根因（证据链全部可复算）

### 1.1 三方交叉：腾讯 kline 在科创板给「股」，行情快照给「手」

| 标的 | 腾讯 kline 同日 vol | 腾讯快照 vol（手） | 比值 | 判读 |
|---|---|---|---|---|
| `1.688035` 德邦科技（科创板） | **4 653 193**（10-16 全天） | 46 532（`amount÷(vol×100)` = 59.5 ≈ price 57.99 ✓ 自洽） | **100.0×** | kline 是**股** |
| `1.688361` 中科飞测（科创板） | 7 448 573 | 74 486 | 100.0× | kline 是**股** |
| `1.600519` 贵州茅台（主板） | 38 502 | 38 502 | 1.0× | 手 |
| `0.300285` 国瓷材料（创业板） | 546 857 | 546 857 | 1.0× | 手 |
| `1.510300` 沪深300ETF | 37 995 085 | 37 995 085 | 1.0× | 手 |

- 腾讯那一侧的取值是**直接探针**（`param=sh688035,day,,,800,qfq` 与不带 `qfq` 两次都回 `4653193`，且 `qfqday` 与 `day` **逐位相同**）⇒ 不是复权键的问题。
- 快照那一侧的自洽式 `amount ÷ (vol×100) ≈ price` 是插件既有的手口径判据（`docs/DESIGN-CHIPS.md` §1）。
- **只有科创板需要 ÷100**；主板/创业板/ETF 实测逐位相等，一根都不许动（多测一个市场就多一份证据，但规则只在实测过的板块生效）。

### 1.2 断层是怎么留下来的

1. `requestKlineRaw` 腾讯优先、东财兜底（`em.ts:2149-2150`）；`fetchKline` 的落盘用 `mergeBars(old, fresh, cap)`（`em.ts:2060-2066`）——**按日期并集**。
2. 两源单位不同 ⇒ 同一份缓存里：**腾讯段（股，×100）+ 东财段（手）**。
3. 线程里只有 `lmt=10` 的增量在动，旧段永远不会被重写 ⇒ 断层长期留存。
4. 实测断层**都出现在最新那一小段**（用户池 3 只全部落在 `2026-09-28` 起）：

| 文件 | 根数 | 断层日 | 旧段/新段 | 旧段中位 | 新段中位 | 段水平比 |
|---|---|---|---|---|---|---|
| `1.688035_101_1.json` | 805 | 2026-09-28 | 795 / 10 | 7 242 678 | 49 238 | **147.6×** |
| `1.688361_101_1.json` | 805 | 2026-09-28 | 795 / 10 | 8 669 257 | 76 762 | **112.9×** |
| `1.688361_101_0.json` | 805 | 2026-09-28 | 795 / 10 | 8 669 257 | 76 762 | **112.9×** |
| `1.688825_101_0.json` | 54 | 2026-09-28 | 44 / 10 | 290 406 830 | 2 193 692 | **132.4×** |
| `1.688035_101_0.json` | 810 | —— | —— | 全段 810 根**都是股** | —— | 无段内断层（见 §7 残留） |

（段水平比不是整数 100：两段是**不同交易日**的真实量能，比值 = 100 × 真实量能比。）

### 1.3 为什么"看起来像只有两只标的受影响"

同一日期上两口径（`fqt=0` vs `fqt=1`）**相差 >20×** 的标的实测只有 3 个：
`1.688035`（9 天，2026-09-28..10-15）、`1.688825`（44 天，2026-07-27..09-24）、
`1.603132`（1 天，0.02× —— 属"一根未完成 bar"的正常差，非量纲）。
⇒ 命中集合 = **用户池里的科创板标的集合**（池里正好这 3 只：`1.688035`／`1.688361`／`1.688825`）。

## 2. 影响面（判据可复算）

**判据 A（段内断层）**：候选位置 `k` 要求 ① 单步 `vol[k-1]/vol[k]` 落在 ≈100× 带内，② 两侧 30 根中位数之比同向且落在 ≈100× 带内（防"一根异常巨量"和"缓慢放量"）。带外（如实测 `0.002667` 的 47.75× 单步、`1.603268` 的 11× 位移）**一律不动**——那是真实量能变化。
**判据 B（绝对量纲）**：同日报价 `amount ÷ (vol×100) ≈ price`（手口径自洽）与缓存 bar 比对，比值 >20 或 <1/20 即判量纲不对（缓存 bar 是盘中快照，物理上不该超过当日全量）。

```bash
# 判据 A：扫全部 101 缓存，找 ≈100× 段内断层（只读）
python3 - <<'PY'
import json,glob,os,statistics,math
K=os.path.expanduser('~/.dsh/dsh-tradewatcher/klines')
med=lambda xs: statistics.median([x for x in xs if x]) if any(xs) else 0
for p in sorted(glob.glob(K+'/*_101_*.json')):
    b=json.load(open(p))['bars']
    for k in range(1,len(b)):
        v0,v1=b[k-1]['vol'],b[k]['vol']
        if not v0 or not v1: continue
        if 1/30 < v0/v1 < 30: continue
        before=med([x['vol'] for x in b[max(0,k-30):k]]); after=med([x['vol'] for x in b[k:k+30]])
        if after and (before/after>=30 or before/after<=1/30) and (v0>v1)==(before>after):
            print(f"{os.path.basename(p)} 断层@{b[k]['date']} 段水平 {before/after:.1f}x  前{k}根/后{len(b)-k}根")
PY
# 判据 B：同日报价 vs 缓存（手口径自洽式）
python3 - <<'PY'
import json,os,datetime
H=os.path.expanduser('~/.dsh/dsh-tradewatcher')
lkg=json.load(open(f'{H}/quotes-lkg.json'))
for r in lkg['rows']:
    if not (r.get('vol') and r.get('amount') and r.get('price')): continue
    p=f"{H}/klines/{r['secid']}_101_1.json"
    if not os.path.exists(p): continue
    d=datetime.datetime.fromtimestamp(r['at']/1000).strftime('%Y-%m-%d')
    same=[b for b in json.load(open(p))['bars'] if b['date']==d]
    if not same or not same[0]['vol']: continue
    print(f"{r['secid']} 快照自洽 amount/(vol*100)={r['amount']/(r['vol']*100):.3f} vs price={r['price']}  缓存vol/快照vol={same[0]['vol']/r['vol']:.3f}")
PY
```

**受影响的对象**（本机实测）：

| 项 | 数量 |
|---|---|
| 用户池（自选 39 + 持仓 10，去重） | 43 只 |
| 其中科创板 | **3 只（1.688035 / 1.688361 / 1.688825）—— 全部命中** |
| 用户池创业板对照 | 4 只，实测手口径，未受影响 |
| 缓存目录里科创板相关文件 | 12 个（含 3 个 v1 老命名 `*_101.json`、1 个周线 `_102_1`、1 个年线 `_103_1`） |

## 3. 修复：三层，全部「只改 vol」

| 层 | 位置 | 做什么 | 为什么在这一层 |
|---|---|---|---|
| ① 源归一 | `em.ts:2169`（腾讯日线解析）、`tencent.ts:239`（`fetchTencentDaily`） | 科创板 `vol ÷100` | 病根在入口：写入缓存前就归一，之后**再也不会产生**股/手混装 |
| ② 段内归一 + 落盘 | `em.ts:1951-1956`（`loadKlineCache` 采纳后）+ `saveKlineCacheRepair`（`em.ts:1976-2005`） | 检出 ≈100× 断层 ⇒ 把**较早那段**对齐到**最新那段**；判不了（最新段 <3 根可用）⇒ **丢较早那段并给出原因** | 缓存是追加式的 ⇒ 以最新段为基准才能保证后续每次增量都不再造断层；源归一之后新段天然是「手」 |
| ③ 读侧报价闸 | `routes.ts:354-364`（筹码路由） | 用**同日报价**（手口径）校验绝对量纲，差 >20× ⇒ 全段 ×1/100 或 ×100 | 段内归一只能保证"自己一致"，保证不了"自己是手"；整段都错（如 `1.688035_101_0`）只有外部参照能抓 |

**三条硬约束的落实**：

- **只改量纲**：归一函数只碰 `vol`（乘除，永不插值/改 OHLC/改日期）；零点 `vol:null`→`null`（**不许 0 顶替**）。
- **写回走锁**：`saveKlineCacheRepair` 用 `updateJsonLocked`（锁内"读磁盘最新 → `mergeBars` 合并 → 原子写回"），条数上限沿用 `KLINE_CAP`；**与常规落盘分开**的关键理由是它**保持 `updatedAt` 原值** —— 用 `saveKlineCache`（会把 `updatedAt` 写成 `Date.now()`）会让收盘后一次修复被读侧判成"休市定稿 ⇒ 免回源"，当天那根新 bar 反而要等到第二天补。
- **不新增请求类型**：三层都复用既有链路（kline 缓存 + 筹码路由**本来就要取**的那次报价），请求次数 0 增加。

## 7. 未做 / 未确认 / 残留风险

1. **整段都是「股」且无段内断层**（实测 `1.688035_101_0`：810 根全股）：

   - 想立刻收敛，可在筹码路由那道报价闸之外，给 K 线路由也接一个报价参照（需多取一次报价，**属新增取数面**，本轮未做）。

|---|---|
| 当前缓存文件 | **199 个**（上限 300）／总体积 **17.2 MB**／中位 **107 KB** |
| 每标的文件数（用户池） | 2 个（101_0 + 101_1）为主（34 只），少数 3–4 个（含 102/103） |
| 用户池全部打开一次需要 | 43 × 2 = **86 个**（加周线 ≈129）——**远低于 300** |
| 剩余 199 − 43×2 ≈ 113 个文件 | 属**指数/商品/ETF 条带**与**已移出自选的旧标的**（`quotes-lkg` 127 行量级） |
| 冷启动代价 | 1 个上游请求（腾讯优先/东财兜底），载荷 50–59 KB，落盘 ~113 KB |

**结论：不值得改成"按标的保留"，只值得（可选）把上限抬高一档。** 理由：

1. **现在的 mtime-LRU 已经等价于"最近看过/更新过的标的"**：读缓存时若需要回源并拿到新数据就会写盘（`refreshKline` → `saveKlineCache`）⇒ 常看的标的 mtime 自然新鲜；被裁掉的一定是"很久没动过"的。按标的保留要么把自选/持仓注入裁剪路径（`em.ts` 与 `store` 的耦合 + 新失败模式），要么在裁剪时读 watch/positions（多一次 IO 且可能读到半写状态）——**收益只是"少一次本来就要付的取数"**。
2. **上限当下不紧**：199/300，用户池全量也只占 86；真正的增长源是"历史遗留 + 条带标的"。
3. 若 Lead 想留更大余量：**把 `KLINE_CACHE_MAX` 300 → 600**（一个常量）即可，代价 = 磁盘从 17 MB 量级到 ~34 MB 量级（按当前中位 107 KB × 600 ≈ 64 MB 上限），扫目录成本 readdir + N 次 stat（600 次 ≈ 数毫秒，10 分钟最多一次）——**无可观测代价**；不必引入"按标的保留"的复杂度。
