## 1. 1 分钟分时数据是否可得

### 1.1 腾讯 `appstock/app/minute/query` —— **实测可得（1 分钟）** ✅

命令（`/tmp/rp-probe/probe.mts`，走 `gatedFetch` ⇒ 先读 robots）：

```
GET https://web.ifzq.gtimg.cn/appstock/app/minute/query?code=sh510300
robots: HTTP 200，0 条规则 ⇒ 放行；by=robots 已读（0 条规则）｜预算 1/5（本小时）
```

返回片段（真实回包，字段 = `HHMM 价格 累计成交量(手) 累计成交额(元)`）：

```
"0930 4.255 92940 39545970.17"
"0931 4.255 469909 200055680.14"
"0932 4.250 571503 243247235.00"
"1355 4.240 6802574 2896672132"
点数 = 177（09:30 → 13:55；A 股半日 120 分钟 + 下午至探测时刻 55 分钟 ⇒ 逐分钟，1 点/分钟）
```

- **粒度 = 1 分钟**（不是 5 分钟）；**时间戳在字段里**（`HHMM`），无秒。
- ⚠ 量的字段是**当日累计**（成交量/成交额），逐分钟值必须**差分**——本项目已在 `minuteTrendPointsOf` 里做，并挂
  `amountDerived: true` + 说明（推导值不当上游直给值用）。

**本机落盘的同链证据（零请求，来自插件自己的归档）** `~/.dsh/dsh-tradewatcher/trends-lkg.json`：

```
key = 1.510050|1（沪深 ETF）｜点数 = 242/日
首点 = { t: 2026-10-15T09:30, label: "2026-10-15 09:30", price, avg(VWAP), vol(每分钟手数), amount(每分钟元), amountDerived: true }
相邻间隔(秒) = [60, 60, 60, 60]      ← 逐分钟
```

### 1.2 东财 `trends2` —— 本次 **未确认**（被 robots 挡住）；粒度可由本机归档实测 ⚠

```
--- push2.eastmoney.com      robots: HTTP 200｜Disallow: /        ⇒ 零请求
--- push2delay.eastmoney.com robots: HTTP 200｜Disallow: /        ⇒ 零请求
--- push2his.eastmoney.com   robots: HTTP 200｜Disallow: /        ⇒ 零请求
[SKIP] push2.eastmoney.com 的 robots.txt 禁止该路径（disallow /）⇒ 按规矩不发请求
```

- **本次未确认**（不是"不可得"）：按纪律`Disallow: /` ⇒ 一条请求都没发。
- **粒度从本机归档可判**：`trends-lkg.json` 里 `1.688035|5`（`ndays=5`）**点数 240、间隔 300 秒**
  ⇒ 东财在 `ndays=5` 时给的是 **5 分钟**粒度；代码注释里另有既有实测（`ndays=1` ⇒ **1 天/242 点** ⇒ 1 分钟）。
- **确认方法**：① 在 robots 允许的窗口/换允许的主机再探一次；② 从**运行中的宿主**读它已取到的 `TrendData`
  （本机 1 分钟链现用腾讯，东财是备用源）——两条路都不需要改代码、也不需要重启。

### 1.3 结论

| 链路 | 1 分钟量能/成交额 |
|---|---|
| 腾讯 `appstock/app/minute/query` | **实测可得**（177 点/本次探测、242 点/日；累计值需差分，已标注） |
| 东财 `trends2`（`ndays=1`） | **未确认**（robots `Disallow: /`）；本机归档显示 `ndays=5` ⇒ 5 分钟，`ndays=1` 的 1 分钟来自既有实测 |
| 东财 `trends2`（`ndays=5`） | **实测可得（5 分钟）**：本机归档 `|5` 条目间隔 300 秒 |

⇒ **1 分钟粒度整体可得**（现役腾讯链就是 1 分钟）；**5 分钟粒度也可得**（东财多日链、以及腾讯链自行降采样）。

## 2. 涨跌家数在「历史某时刻」是否可得

### 2.1 结论先说

| 问 | 判定 | 依据 |
|---|---|---|
| ① 当日**日内序列**（A/D 家数） | **实测不可得** | `breadth.json` **每天只留一行**：`BreadthDay { up, down, even, amount, at, final }`；`record()` 是**覆盖写**（`this.file.days[day] = next`），`final` 之后冻结 ⇒ **只保留"最后一次观测"**，没有日内序列 |
| ② 历史日"某时刻" | **实测不可得** | 历史只有**每日一个快照**（窗口 `BREADTH_WINDOW=60` + 30 天余量）；`/breadth` 的 `history()` 给的是每日值，不是时刻值 |
| 历史**某日**（收盘/最后观测） | **实测可得** | 同上：每日一行，≤90 天 |
| 当日**当前时刻** | **实测可得** | `/breadth` 每次返回 `current`（含 `asOf` 与来源：源 A 指数 `f104/f105/f106` / 源 B 东财 clist 自统计） |

### 2.2 关键代码证据（读码，未跑上游）

```
src/host/breadth.ts:154  async record(now, data) { ... this.file.days[day] = next ... }   // 覆盖写
src/host/breadth.ts:19   interface BreadthDay { up, down, even, amount, at, final }
src/host/routes.ts:539   await breadth.record(Date.now(), current)   // 每次 /breadth 请求刷新当日那一行
src/host/routes.ts:556   prev = breadth.history(BREADTH_WINDOW, today)   // 分位用"每日值"序列
```

仓内**没有**任何"A/D 家数 × 时刻"的存储（全仓 grep `f104/f105/f106` 只出现在指数/板块行情的解析与 `/breadth` 路由，
没有序列落盘；护盘 `RescueIntradayPoint` 只有 `level/score/timeAdjMult/superVsAvg/persistShare`，**不含家数**）。

### 2.3 对"护盘触发时全市场对比"的含义

- **能做的**：触发瞬间（或悬停时）读一次 `/breadth` 拿**当时**的 A/D 与成交额，与**每日历史**比（分位已有）；
- **不能做的**：回看"上周二 10:37 的 A/D"——**没有这份数据**（当日也只有最后一行的覆盖结果）；
- 若要"触发时刻的日内对比"，只能二选一：(a) 只展示**实时那一次**读数（不落盘、零新增请求）；(b) 新增日内采样落盘
  ⇒ **会新增上游请求**，且需要你批准（本探针不改代码）。

## 3. 六通道「同一时刻」的瞬时超大单净额

### 3.1 结论

| 问 | 判定 | 依据 |
|---|---|---|
| 六只**同一请求、同一时刻**能一起拿到吗 | **实测可得** | 上游是批量行情：一次 `ulist.np/get?secids=…` 同刻返回六只；本地采样环每拍也是**同时**写六只 |
| 上游给的字段是**瞬时**还是**累计** | **累计**（当日）⇒"瞬时"**上游不可得** | 字段语义：`f62` 主力净额 / `f66` 超大单净额（东财 ulist），与当日累计成交额同族 |
| "某一时刻的瞬时"能否得到 | **本地可得（差分）** | 采样环 30 秒（尾盘 15 秒）⇒ 相邻两拍差分 = 该窗口的净增；这正是 `脉冲`/`persistShare` 算法的做法 |
| 六只的**分通道**瞬时值有落盘吗 | **部分**：当前快照 `snapshot.etfs[].superNet` 有六只同刻（累计）值；`rescue-log` 的 5 分钟 `intraday` **只落聚合值** `superVsAvg`，不落六只分通道值 | `RescueIntradayPoint` 字段表 + `etfPeak` |

> ⚠ **本次没有实测东财返回**（`push2*/robots.txt` 全为 `Disallow: /`）⇒ 上面"上游是累计值"的依据是
> **代码字段注释 + 本地落盘语义**（`superVsAvg` 与 `脉冲` 都由相邻采样差分而来），属**未确认上游回包**。
> 确认方法：同上（robots 允许时探一次 `fields=f12,f14,f62,f66,f124`，看回包是单调累计还是窗口值）。

### 3.2 对悬停联动的含义

- 悬停时**能拿到**：最新快照里**六只同刻**的累计超大单/主力净额（一次采样同刻写入）；
- 想要"这一刻的瞬时"，需要在内存里保留**最近两条**采样（各通道 `superNet` 之差）；目前 `rescue-log`
  只持久化**聚合**的 5 分钟值 ⇒ 若联动要"按时刻悬停六只"，要么复用最新快照（六只同刻 ✓，但是累计），
  要么由宿主在快照里**多带一条"上一拍"**（属改动，需你定；本探针不改）。

## 4. 现有分时链路的每主机请求数（联动与切换是否会新增请求）

### 4.1 每主机请求量（按实现的采样/缓存口径估算）

| 链路 | 口径（代码常量） | 每小时请求（估） |
|---|---|---|
| 护盘采样（行情 + 分单资金流） | `intervalSec=30`（尾盘 15s）⇒ 2–4 拍/分；**一次批量**取全部通道 | 东财 `push2delay` ≈ **120–240** |
| 分钟序列刷新 | `MINUTE_REFRESH_MS=60_000`，6 通道各 1 次（腾讯优先，东财兜底） | 腾讯 `web.ifzq.gtimg.cn` ≈ **360** |
| `/breadth` 家数 | `BREADTH_COUNT_TTL_MS=120_000`（源 A 指数行情 1 次；源 B 分页只在源 A 缺失时） | ≈ **≤30**（只有页面真在读时才发） |
| 宏观 / 归档（**门禁链路**） | `HOST_BUDGET_MAX=5 / 3600s`，先读 robots | **≤5/主机/小时**（这条预算只约束它们） |
| **本次探测** | 同上门禁 | 腾讯 1/5（其余 0：robots 禁止） |

> ⚠ 口径澄清：**"同主机 ≤5 次/小时"是 `robotsGate` 对门禁链路（宏观/归档）的预算**；
> 报价/分时链路走的是**熔断器 + TTL**（上面 360/h 那一档），不是 5/h。两者不同，别混用。

### 4.2 「联动读取是否只命中本地缓存」

| 读法 | 是否新增上游请求 | 依据 |
|---|---|---|
| `GET /tradewatcher/rescue`（面板/悬停复用同一次响应） | **不新增**（例外见下） | 路由用 `rescue.snapshot()`（**内存快照**）；仅当"本会话还没有快照"时 `ensureFresh()` 会补采一次，且有 `AUTO_TRY_COOLDOWN_MS = 20_000` 冷却 |
| 同一响应内既有字段（六通道 `etfs[]`、`intraday`、`today`、`history`） | **不新增** | 全部是快照/落盘数据的投影，无上游调用 |
| `GET /tradewatcher/breadth` | **可能新增（有界）** | 走 `resolveBreadthCount(..., cache)`：缓存命中（120 秒内）⇒ 不打上游；过期 ⇒ 1 次源 A（源 B 才分页） |
| `?force=1`（强制采样）/ 悬停触发 `sampleNow` | **会新增** | `force=1` 明确要求实时采样 |

**结论**：只要联动与切换**复用已经到达浏览器的那份 payload**（同一次 `/rescue` 响应里的 `snapshot` + 前端已持有的 breadth 数据），
**不新增任何上游请求**；唯一会"因读而生"的是 `/breadth` 的 120 秒缓存过期那一次（≤30/h）与显式的 `force=1`。
