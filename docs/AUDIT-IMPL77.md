## 1. 第 1 项：LKG 装载 60–65 ms → ~5 ms（热条内联 + 冷条懒加载）

### 1.1 做法

清单升级 **v4**：`entries[]` 里**最近 N 条**（`TREND_LKG_HOT_MAX = 8`）直接内联 `trend`，
其余条目只留 `{key, at, seq, bytes}`（**冷条**）。装载只读一个文件；冷条在首次访问
`ensure(key)`（异步）时才读分片，同时在后台 `ensureAll()` 预热（读完若产生新热条，补写一次清单）。

- **预算守卫**（`planHotEntries`）：热条数 ≤ N，且内联后清单 ≤ `TREND_LKG_MANIFEST_MAX_BYTES`（512 KB）；
  预算不够就少放几条（宁可变冷，也不越界）。所以"把 N 调大"不会突破单次写红线（测试 ⑥ 给出无预算的对照：必然越界）。
- **读路径**：`lastGoodTrend()` 改异步（唯一生产调用点在 async 的 `trendWithFallbackRaw` 里），
  热条同步命中、冷条按需读一个分片（≈0.5 ms），并发同 key 只读一次。
- **写路径串行化**：装载升级、后台预热、业务刷新可能同时触发写，并发写会撞同一个 `*.tmp`
  （实测遇到一次 `ENOENT rename trends-lkg.json.tmp`）⇒ 加 promise 链排队。

### 1.2 实测（真实数据 111 条 / 2.3 MB，`/tmp/q6-lkg` 副本）

```
改前（AUDIT-IMPL76 的分片版）：装载 60–65 ms（111 个分片逐个读）
改后（v4 热条 8 条）：装载 0.7 / 2.4 / 3.6 / 3.9 / 5.4 ms（5 次）
                      hotLoaded=8、cold=103，清单 120 049 B
冷条后台预热：ensureAll 60–83 ms（**不在启动路径上**）
一次业务刷新：只写清单（≈120 KB，含热条）或 1 个分片（≈18 KB），单次 ≤ 512 KB
```

### 1.3 断言与注入（`src/host/trendLkgShards.test.ts` 7 例）

| 判据 | 断言 | 注入（反例） |
|---|---|---|
| ① 单次写 ≤ 512 KB | 40 条 × 242 点：单条分片 < 64 KB、清单 ≤ 512 KB；旧形状 blob > 512 KB | 退回"整份 blob" ⇒ `maxWriteBytes` 越界 ⇒ 红 |
| ② 装载有上界 + 懒加载等价 | 装载只读热条（`loadedShards=8`、`cold=103`）、`loadMs < 30 ms`；`ensureAll()` 后与重启前**逐字节相同** | 删一个冷分片 ⇒ `missing ≥ 1` 且不再等价（测试内直接执行） |
| ③ 保留口径 | 守恒 `存活 + droppedTotal == 总数`；`caps`（含 `hotMax`/`manifestMaxBytes`）进清单 | 静默截断 ⇒ 守恒不成立 ⇒ 红 |
| ⑥ N 调大 | 预算把热条夹在 512 KB 内（< 64 条也可能）；预算为 0 ⇒ 0 条热 | 无预算"取前 64 条" ⇒ 实测 > 512 KB ⇒ 红 |

## 2. 第 2 项：`/kline` 的 `pct:null` 与 `/trend` 的逐点 `label` 瘦身

### 2.1 编码（只裁冗余，语义不变）

- `/kline`：`pct === null` **不发送**（缺省 ≡ 上游没给）；`pct: 0` 是**真实涨跌幅**，照发。
- `/trend`：**单日**序列（所有点都是 `YYYY-MM-DD HH:mm` 且同一天）⇒ 逐点 `label` 只留 `HH:mm`，
  日期上移到 `labelDay`，标 `labelFormat: 'hhmm'`；跨天 / 格式不符 ⇒ **原样不动**（多日轴靠 label 里的日期分段）。
- 只作用于**回包**：内存/落盘/归档仍是完整形状（老版本回滚可读）。

### 2.2 读侧归一（双编码兼容）

`src/client/chartWire.ts`：`klinePctOf`（缺省 ⇒ `null`，**不当 0**）、`normalizeTrendLabels`（缺 `labelDay` 时原样）、
`normalizeKlineDays`。统一在 `chartCache.ts` 的取数收口处应用 ⇒ 下游（图表轴、脚注、迷你卡）全部不用改。

### 2.3 实测（真实数据）

```
/kline  0.000636 日线 240 根（pct 全 null）：24 333 → 21 693 B（−2 640 B，整包 −10.85%）
/trend  122.XAU 2026-10-13 242 点（单日）  ：24 022 → 21 405 B（−2 617 B，整包 −10.89%）
        其中 label 字段 3 872 B → 约 1 255 B（−68%）
两项字段合计：6 512 → 1 255 B ⇒ **−80.7%**（目标 ≥ −30%）
```

### 2.4 断言与注入（`src/host/wireSlim.test.ts` 3 例）

| 判据 | 断言 | 注入（反例） |
|---|---|---|
| ① 字节 | `pct:null` 省 ≥1.2 KB、单日 label 省 ≥2.4 KB；两项合计 ≥ −30%（按字段实际占用算） | 退回旧编码（每根带 `pct:null`、每点带完整标签）⇒ 节省量 0 ⇒ 红 |
| ② 双编码等价 | 紧凑编码归一后与完整编码**逐点 deepEqual**；`pct` 缺省 ⇒ `null`、`0` 仍是 `0` | 缺省当 0 / 不补日期 ⇒ 不等 ⇒ 红 |
| ③ 两种编码都能渲染 | `sessionAxis`（分时轴）与 `trendDayAxis`（多日分段）在两种编码下**输出相同** | 只支持新编码的归一 ⇒ 紧凑编码渲染不同 ⇒ 红 |

## 3. 第 4 项：清理 2.3 MB 老备份（校验通过才删 + 摘要留痕）

### 3.1 规则

- **迁移完成**：把每个分片**读回来解码**，逐条与迁移前的 trend 指纹比对；`verifiedShards === entries` 才删备份。
  清单写 `migratedFrom = { v:2, ts, file, bytes, entries, sha256, verifiedShards, verified, reason, removedAt }`。
- **已有备份**（v0.106 在真实目录留下的那份）：装载时 `verifyExistingBackup()` —— 备份条目数/`at`/trend 指纹
  与清单+分片逐条比对；全对 ⇒ 删除 + 摘要；任一不对 ⇒ **保留** + `reason` + console.warn（界面/日志可见）。
- `sha256` 用 Node 内置 `crypto`（**零新增依赖**），记的是老文件**全文**的哈希 ⇒ 删掉之后仍可核对"当时删的是哪份"。

### 3.2 实测

```
/tmp/rv-perf/home-io3（真实数据的副本，111 条 / 2 342 741 B）：
  [tradewatcher] trends-lkg 迁移完成并校验通过（111/111 条）⇒ 已清理老备份 trends-lkg.v2.json.bak（sha256 1c127020f334…）
  备份文件已不存在；清单 migratedFrom.verified=true / verifiedShards=111
真实数据目录 ~/.dsh 里那份 2 342 741 B 的备份：**未手工删除**（纪律），下一次宿主重启时由上述代码校验后清理
```

### 3.3 断言与注入（`trendLkgShards.test.ts` ④⑤⑦）

| 判据 | 断言 | 注入（反例） |
|---|---|---|
| ④ 成功 | 备份被删；`migratedFrom` 的 `bytes/entries/verifiedShards=3/verified=true/removedAt/sha256` 与老文件 sha256 一致；清单里也有 | "直接删不看校验"的摘要 `verifiedShards=0` ⇒ 对不上 ⇒ 红 |
| ⑤ 失败 | 注入一条分片校验失败 ⇒ 备份**保留**、`verified=false`、`reason` 点名该 key、`removedAt=null`、清单同样记录 | "失败也删" ⇒ 备份保留断言红 |
| ⑦ 已有备份 | 校验通过 ⇒ 清理 + 摘要；备份内容被篡改（`at` 不一致）⇒ **保留** + `reason` 点名 | 篡改后仍删 ⇒ 红 |
